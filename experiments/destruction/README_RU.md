# Визуальные обломки и физика блоков — исследование для 0.3.3

Дата: 07.11.2026. База: `535de72501f92616c32e29ec7fab1c4adadf417e`, Minecraft 1.21.1, NeoForge 21.1.264, Java 21. Владелец подтвердил одиночный мир и игру на этой базе и выбрал **визуальные обломки и физику блоков** как приоритет.

Это исследование, **не добавление модов в сборку**. `modlist.json`, установщик, сервер и игровые настройки базы не изменены. Кандидаты не проверены запуском Minecraft. Их JAR скачаны только для анализа, сверены с SHA512/SHA1 Modrinth и не включены в Git. Метаданные и результаты: [candidates.json](candidates.json).

В [исходниках Incoming v3.10.4](https://github.com/zentixua/incoming/blob/v3.10.4/mod/src/main/java/ua/zentix/incoming/IncomingConfig.java) подтверждены:

- `world.debris_stay=true`: часть обломков остаётся на земле; выключение меняет результат разрушения, а не просто FPS.
- `world.collapse=true`: подземный взрыв обрушает крышу полости. Это не глобальная физика всех построек.
- `performance.work_ms_per_tick=30` (диапазон 5–45): бюджет тяжёлых работ, а не обещание фактической длительности каждого тика. Предложение для отдельного замера — 5–10 мс; меньший бюджет может растянуть формирование разрушений.
- `nuclear.fires_per_detonation=20000`: потенциально существенная нагрузка; снижение меняет последствия удара, поэтому автоматически не применяется.
- Клиентское `blast_effects`: отключение скрывает эффекты Incoming, **но не заставляет другой мод заменить их**; ядерные взрывы и попадания ПВО остаются собственными эффектами Incoming.

[DebrisSpawner](https://github.com/zentixua/incoming/blob/v3.10.4/mod/src/main/java/ua/zentix/incoming/warhead/DebrisSpawner.java) создаёт `DebrisEntity`; у ядерных разрушений есть собственные [расчёты обрушения](https://github.com/zentixua/incoming/blob/v3.10.4/mod/src/main/java/ua/zentix/incoming/nuclear/world/Collapse.java). Это основание сначала проверить имеющиеся эффекты, а не накладывать второй движок разрушения.

### Physics Mod: найденное предупреждение не равно подтверждённому вылету

В проверенных JAR **3.0.35 и 3.0.34** `physicsmod.mixins.json` ссылается на отсутствующий `net/diebuddies/mixins/create/MixinAbstractContraptionEntity.class`. Это зафиксировано как риск интеграции с Create, а не как доказательство падения клиента.

В [issue #1264](https://github.com/haubna/PhysicsMod/issues/1264) речь шла о Pro v188j с Create 6.0.10. Автор написал, что сообщение может не мешать работе; заявитель затем [подтвердил другую причину вылета](https://github.com/haubna/PhysicsMod/issues/1264#issuecomment-6620285385). Issue закрыт. Нельзя переносить исходный заголовок отчёта в список доказанных конфликтов Lite 3.0.35. Откат на 3.0.34 не устраняет найденную ссылку и пока не обоснован.

В JAR Lite 3.0.35 подтверждены пункты интерфейса `Physics Max Objects`, `Activation Distance`, `Lifetime (Blocks)`, `Block Physics` и режимы `Off` / `Fractured` / `Blocky` / `Particles`. Начальная гипотеза для слабого ПК: лимит 128 объектов, дистанция 16 блоков, короткая жизнь 1–2 секунды; проверить допустимые значения и единицы в GUI, включать только нужные эффекты блоков. Это **предложение для замеров**, не готовый JSON и не испытанный пресет. Не включать серверное обрушение или дополнительные физические эффекты без отдельного теста. [Страница бесплатных возможностей](https://minecraftphysicsmod.com/features) и [официальная загрузка](https://minecraftphysicsmod.com/download).

### FBP: проверены исходники именно выбранного выпуска

Скачаны runtime и sources JAR **21.1.6.0**, оба проверены по опубликованным SHA512/SHA1. В runtime подтверждены Minecraft `[1.21.1,1.22)`, NeoForge `[21.1,)`, Java 21; все классы, перечисленные в двух mixin-конфигах, присутствуют.

В исходниках проверены `FBPConfig`, `FBPTerrainParticle`, `MixinParticleEngine` и mixin интеграции с Sodium. Сигнатура `BlockRenderer.renderModel`, поле `BlockOcclusionCache.cachedPositionObject` и метод `shouldDrawSide`, на которые опирается интеграция, присутствуют в фактическом Sodium **0.8.13** из базы. Это ограниченная статическая проверка, не успешная загрузка mixin и не полный тест рендера.

FBP заменяет обычные частицы блоков и обработку `ParticleEngine.destroy`. Это **не универсальный перехват каждого удалённого взрывом блока**. Удары Incoming и другие массовые изменения мира могут использовать собственный путь разрушения и собственные обломки. Если в игровом тесте осколков нет, одной установки FBP недостаточно: понадобится изучение конкретного события/пакета и, возможно, ограниченный клиентский адаптер. Создавать эффект для каждого блока ядерного кратера без лимита нельзя.

Подготовлен [предлагаемый конфиг FBP](fbp-config.proposed.json), **не подключённый к сборке**. Ключи сверены с `FBPConfig.java` выбранного sources JAR. Для полноразмерного одиночного куба `particlesPerAxis=2` даёт 8 частиц вместо 64 при стандартном значении 4; для составных форм результат отличается. Жизнь 10–25 клиентских тиков, физика воды/сущностей, дождь, снег, дым, дополнительные эффекты и анимации установки выключены; столкновения с блоками сохранены. Это сокращает объём моделирования относительно стандартных настроек, но измерений FPS ещё нет. Общий жёсткий лимит числа осколков этим конфигом не задаётся.

Перед интеграцией нужно развязать стандартные горячие клавиши FBP: `R` — заморозка частиц — пересекается с привычной перезарядкой оружия; также проверить `I` и `X`. Не перезаписывать существующий `options.txt` и `config/fbp/config.json`. В едином Optimized-профиле уже установлены минимальные частицы — отдельно проверить, какие эффекты с ними видны.

## Конкретный порядок продолжения

1. **Контрольная база:** сохранить рабочую установку `535de72`. На копии тестового мира отдельно проверить TNT, оружие Superb Warfare и TaCZ, обычный удар Incoming, затем небольшой ядерный удар. Снять исходные FPS/время кадра и MSPT/TPS, оценить собственные обломки Incoming. Серверный тест — после принятия EULA администратором.
2. **A/B Physics Mod:** только клиентский Lite 3.0.35, без FBP и без других новых модов. Проверить главное меню, загрузку/повторный вход, Sodium, сборку и движение механизма Create, каждый источник взрыва, отсутствие двойного урона и чрезмерных эффектов. Ограничить объекты/радиус/время через GUI. Сохранить обезличенные логи.
3. **Отдельное A/B FBP:** убрать Physics Mod из этой тестовой установки, поставить только FBP 21.1.6.0 с предлагаемыми настройками. Сравнить реальную видимость обломков и нагрузку на тех же сценах. Изменения конфигов только в копии, с возможностью отката.
4. **Выбрать один визуальный слой:** не ставить Physics Mod и FBP вместе по умолчанию. Урон и серверное разрушение оставить владельцам соответствующих механик; проверить дублирование дыма/волн Explosion Overhaul и Incoming. Проценты совместимости на авторских страницах не заменяют проверку этого набора версий.
5. **После успешного теста:** закрепить выбранный `version_id`, `client_only=true`, хеши и совместимый консервативный конфиг; провести все пути сборки (Windows EXE + официальный Launcher, `.mrpack`, сервер без клиентского JAR). Затем повторить тест с двумя игроками и на слабом ПК. Выпуск автоматически не публиковать.

В каждом сценарии сравнивать одну и ту же копию мира, позицию камеры, настройки и объём разрушения; прогреть чанки. Зафиксировать CPU/GPU, системную и выделенную RAM, ОС/Java, FPS/время кадра, MSPT/TPS, продолжительность зависаний и число ошибок. Не выдавать результат на одном ПК за обещание производительности всем игрокам.
