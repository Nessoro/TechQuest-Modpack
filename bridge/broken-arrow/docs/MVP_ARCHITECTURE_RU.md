# Архитектура MVP — Broken Arrow × TechQuest

Статус: дизайн, не рабочий мод. Не касается `main`; отдельная ветка.

## Топология

```text
 [Игрок Minecraft]                         [Командир / Broken Arrow]
        |                                            |
 [NeoForge Bridge Mod]                    [Companion UI] (MVP-B)
        |                                            |
        +-------- HTTPS / JSON + auth ---------------+
                             |
                        [Bridge Server]
                      (состояние операций)
                             |
                   [NeoForge Bridge Mod]
                             |
          [Minecraft server thread / command dispatcher]
                             |
                 [/incoming bunker at x y z]
                             |
                       [Incoming 3.10.4]
                             |
           [действие в мире + подтверждённый статус]
                             |
                 [Bridge Server → Companion UI]

  [Broken Arrow LuaNode / GameAPI] → (?) внешний канал
                    только если официально разрешён (MVP-A)
```

## MVP-B: настоящий пользовательский путь без интеграции в процесс Broken Arrow

1. Minecraft-игрок отмечает точку и нажимает `Запросить поддержку`. Его запрос отправляется от серверной NeoForge части (не напрямую с клиента) со статусом `REQUESTED`.
2. Bridge Server проверяет размер/срок/UUID заявки и публикует её командиру в companion-панели. Командир, находясь в Broken Arrow, **в отдельном окне** видит координаты, тип удара и кнопку подтверждения.
3. Командир нажимает `Approve`. Для исходящих приказов, созданных самим командиром в companion-панели, первый шаг можно пропустить: но и тогда адрес/координаты проверяются.
4. NeoForge Bridge Mod асинхронно получает одобренное задание, валидирует измерение, позицию, лимиты и существование нужного Incoming. На **главном серверном потоке** вызывает исключительно поддерживаемую команду (`incoming bunker at x y z` для B-2, либо `incoming missile at x y z`). Никакого RCON.
5. В ответ публикует `ACCEPTED_BY_INCOMING` либо `FAILED` с машинным кодом. Подтверждения *реального попадания* в MVP нет: отображается `IMPACT_UNVERIFIED`. Нельзя показывать `HIT` только по результату вызова команды.
6. Командир видит обновление в companion-панели. Оба игрока продолжают свои игры независимо.

## MVP-A: возможный штатный BA-adapter

Только если в Help / официальном API редактора Broken Arrow задокументирован внешний I/O и его работа допускается правилами игры. Событие сценария → разрешённая транспортная функция → `Bridge Server`. Дальнейшая часть системы не меняется. При отсутствии внешнего I/O этой стрелки **не существует**. Не симулировать её чтением памяти, инъекцией DLL, перехватом пакетов, макросами или подменой EAC.

## Компоненты

### Bridge Server

- Отдельный процесс/сервис с управляемым адресом; в MVP локально привязывать только к `127.0.0.1`. Для двух ПК — приватная сеть, например Tailscale, плюс firewall и защищённый транспорт; никогда не публиковать неаутентифицированный API в интернет.
- Отдельные ключи `minecraft` и `commander`. Никогда не передавать их игровым клиентам. На сервере — whitelist, rate limit и журнал запросов без секретов.
- Хранение idempotency `operation_id`, TTL, статус, краткий журнал и lease для одноразовой доставки задания. Повторный HTTP запрос не порождает второй удар.
- Предлагаемые конечные точки (НЕ реализованы):
  - `POST /v1/strikes` — создать заявку (Minecraft) или собственный приказ (командир).
  - `GET /v1/strikes?state=requested` — для commander.
  - `POST /v1/strikes/{operation_id}/approve` — approve/reject.
  - `GET /v1/dispatch` — server-side NeoForge получает только одобренные задания.
  - `POST /v1/strikes/{operation_id}/result` — server-side Minecraft сообщает результат.
  - `GET /v1/strikes/{operation_id}` — пользовательский статус с проверкой прав.

### NeoForge Bridge Mod

- Собственный `modid=techquest_bridge`, Java 21; отдельный Gradle-проект в `bridge/broken-arrow/minecraft-mod/`. Серверная логика с опциональным клиентским UX; ни один файл/мод TechQuest не заменяется.
- На старте проверять Minecraft/NeoForge/Incoming версии; отсутствие Incoming → disabled/read-only, а не падение всей сборки.
- В HTTP-ответе только *данные*, не доверять пришедшим строкам команд. Команда собирается на сервере из allowlist и строго проверенных целых координат.
- Не делать блокирующее HTTP/I/O в ServerTickEvent; результат опроса планируется на Minecraft server thread через `MinecraftServer.execute(...)`.
- Нацеливание ограничить текущим миром и заранее разрешённой областью; лучше до тестов только `minecraft:overworld`. Не запускать при отключении bridge флага, без резервной копии мира или на общем сервере без согласия администратора.

### Incoming

В тестовом мире, с разрешением оператора/консоли:
`/incoming bunker at 120 70 -340` — авиаудар B-2.
`/incoming missile at 120 70 -340` — крылатая ракета.

В MVP allowlist: `bunker`, `missile`, по одному боеприпасу; блокировать `nuke`, `now`, `salvo`, `rocket`, произвольные строки и маршруты. Не вызывать внутренние непубличные классы Incoming, пока API не согласован. Команда успешна — *приказ отдан*, но попадание ещё не доказано.

## Протокол и безопасность

Стартовая форма данных в `../protocol/strike-order.schema.json`. Все операции имеют уникальный `operation_id` и срок действия, сервер повторно валидирует запрос. По умолчанию лимит для тестов — одна принятая операция за 60 секунд, не более одной одновременно; остальные отклоняются. UTC-время используется для TTL, игровое время (если доступно) — отдельное поле. Отключение Bridge Server, сбой сети или отсутствие игрока Minecraft — отказ без создания нового залпа.

### Статусы

`REQUESTED` → `APPROVED` или `REJECTED` → `LEASED` → `ACCEPTED_BY_INCOMING` или `FAILED`; `EXPIRED` может завершить непринятую заявку. После `ACCEPTED_BY_INCOMING` показывать `IMPACT_UNVERIFIED` до появления подтверждённого механизма отслеживания. Значения `CONFIRMED_HIT` и `TARGET_DESTROYED` запрещены без независимых игровых событий/измерений.

## Координаты

Без документированного API позиционирования BA координаты **не синхронизируются**. В MVP-B цель указывается игроком Minecraft или вручную через companion UI. Для возможного MVP-A завести отдельную калибровку (опорная точка, смещение X/Z, масштаб, поворот, высота поверхности, размер карты) и отдельное измерение; запрещены прямые предположения `BA_x == MC_x`.

## Тесты и критерии готовности

- Рабочий тест `request→approve→command→result` на двух процессах без запуска BA через companion UI; одна команда = один удар.
- Отказы: неверный ключ, повтор `operation_id`, истёкший срок, неразрешённая координата или измерение, сервер не в сети, отключённый Incoming, кэшированный пакет, повторный опрос, разрыв между запуском и ACK.
- Проверка действительного `bunker` / `missile` на копии мира и сервере 21.1.264 с Incoming 3.10.4.
- Сравнить тики/MSPT, активные чанки, статус сервера до/после, убедиться что существующий TechQuest без bridge JAR работает по-прежнему.
- Закрепить **отдельный** CI для bridge. Не редактировать CI и установщик основного профиля до приемки.
- В Broken Arrow проверить наличие документированного внешнего I/O в редакторе; без него поддерживать только companion.

## Что отложено

Реальное попадание, разведка из мира MC внутрь BA, карты BA, 3D-артиллерия, подкрепления, обмен боевыми задачами, автоматическая трансляция координат, изменение интерфейса Broken Arrow — за пределами MVP до подтверждения API и игрового теста.
