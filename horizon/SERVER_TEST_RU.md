# Подготовка изолированного сервера Horizon 26.3

Владелец явно принял Minecraft EULA для изолированного серверного теста
ответом «Да» в текущей сессии. Согласие не подтверждает вход Microsoft или
наличие игровых ресурсов. Повторное подтверждение того же теста не требуется.
Существующий NeoForge-сервер и его миры для эксперимента не используются.

## Нативные инструменты

Workflow `horizon-native-runtime.yml` собирает из официального Horizon
`c78187dffffb60f31517eadcb87413386e8ce729` четыре Linux x86-64 инструмента:
`horizon-engine`, `horizon-prepare`, `horizon-server`, `horizon-ctl`.
Сборка `fast --locked --no-default-features` отключает звук, контроллеры
и необязательные сетевые возможности движка. Временный CI-артефакт содержит
исполняемые файлы, LICENSE, research-lock.json, контрольные суммы и отчёт.
Minecraft, ресурсы сторонних модов, учётные данные и миры в него не входят.
Это инструменты разработчика, не новый установщик и не релиз модпака.

`--help` и `--launch-api` проверяют лишь загрузку исполняемых файлов.
Даже успешный workflow **не означает запуск сервера или рабочего Horizon-модпака**.

Подтверждённый прогон: [Actions #42799185254](https://github.com/Nessoro/TechQuest-Modpack/actions/runs/42799185254),
TechQuest commit `a2aa753`, успешно завершён 10 ноября 2026. Все четыре бинарника
запущены с `--help`; JSON Launch API движка прочитан. Создан
[временный артефакт инструментов](https://github.com/Nessoro/TechQuest-Modpack/actions/runs/42799185254/artifacts/13756026205).
Это проверка в Ubuntu CI, не запуск мира в текущей облачной среде.
14 unit-тестов Horizon прошли локально и в CI; дополнительно локально прошли
45 тестов старой базовой части этой экспериментальной ветки. Эти 45 тестов
не следует приписывать текущему NeoForge `main` или игровому порту.

## Что требуется для настоящего запуска

1. Подготовленная папка ресурсов **26.3**. Официальный
   `horizon-prepare` импортирует файлы установленной Minecraft; сам игру не скачивает.
   Подготовку можно выполнить в официальном Horizon Launcher на своём компьютере
   или локально из проверенных официальных загрузок (см. результат ниже).
   Сервер не требует входа игрока Microsoft, чтобы просто загрузить мир, но требует
   подготовленные файлы. Для игрового клиента сохраняется проверка лицензии
   официальным launcher; её не обходим. Пароли и токены передавать не нужно.
2. Вся подготовленная папка, включая `horizon-resources.json`,
   `horizon-prepare.json`, `facts.json`, `block-tags.json`, `registries.json`,
   `commands.json`, текстуры и шрифты. Перечисление не исчерпывающее: движку нужны
   и остальные результаты подготовки. Для подготовки исходных файлов нужен Java 25;
   готовый нативный сервер Java для игры не запускает.
3. Шесть content-модулей из совместного workspace: четыре YUNG's, Terralith,
   `techquest_yungs_shared`. Их отдельно проверяет официальный SDK; текущая проверка
   сборки движка их не загружает и не публикует.
4. Новая отдельная папка теста, только loopback, whitelist и `online-mode=true`.

## Предварительная проверка разработчика

Из корня репозитория (это **не пользовательский способ установки**):

```bash
python horizon/tools/server_preflight.py \
  --resources /path/to/prepared/26.3 \
  --tools /path/to/native-tools \
  --work /path/to/five-together \
  --server-dir /path/to/new-isolated-test \
  --accept-eula
```

Скрипт только читает: не запускает процессы, ничего не скачивает, не пишет
`eula.txt`, не меняет ресурсы и миры. Он проверяет версию/схему подготовки,
два записанных SHA-256 производных файлов, наличие основных ресурсов,
происхождение и SHA-256 инструментов, манифесты модулей, владельцев namespace
и отдельную пустую папку теста. Возвращает 2 при проблемах. Вывод не включает
абсолютные пути и содержимое игровых файлов. Самописные JSON или тестовые
fixtures не заменяют официальную подготовку и **не доказывают право владения**.

Даже `preflight_passed=true` не является полной проверкой ресурсов, SDK,
запуска мира или портирования. Нужны реальная загрузка всех шести модулей,
`Done`, сохранение, штатная остановка и повторное открытие мира; затем вход
лицензированного клиента, генерация структур, мультиплеер и замеры нагрузки.
Не использовать `--benchmark` как проверку модов: он их не загружает.

## История сетевого ограничения (снято)

10 ноября 2026: готовая папка `horizon-resources.json` в `/workspace` и `/tmp`
не обнаружена. Предварительная проверка с `--accept-eula` вернула 2 и явно
записала `eula_consent_provided=true`, `server_boot_tested=false`; папка сервера
и `eula.txt` не созданы.

Проверка `https://piston-meta.mojang.com/mc/game/version_manifest_v2.json`
завершилась `CONNECT tunnel failed, response 403`. Текущая применённая сетевая
политика не включает домены игровых загрузок Mojang. Изменить её доступными
инструментами этого чата нельзя. Для получения исходных файлов потребуются
настройки доступа к официальным `piston-meta.mojang.com`,
`piston-data.mojang.com`, `libraries.minecraft.net` и
`resources.download.minecraft.net`; дополнительные перенаправления проверяются
отдельно. Альтернатива — предоставить рабочей среде уже подготовленную
владельцем папку 26.3. Снятие сетевого ограничения само по себе не подтверждает
владение игрой, успешную подготовку или работоспособность модов.

## Реальный серверный тест — 10 ноября 2026

После обновления среды запросы к Mojang проходят. Официальные metadata 26.3,
client/server JAR, 114 библиотек и asset store получены в отдельный кеш
`/workspace/horizon-runtime/minecraft`. Проверены размеры и SHA-1: всего
5265 файлов, включая metadata и индекс. Версия metadata и JAR совпадают с
`research-lock.json` закреплённого Horizon. Подготовка выполнена настоящим
`horizon-prepare` и JDK Temurin 25.0.5; `--complete` и затем `--check` прошли.
Аккаунты и пользовательские папки launcher не использовались.

Нативные инструменты из Actions #42799185254 скачаны и проверены по всем
четырём SHA-256 из `build-result.json`. Дополнительно локально собраны
`horizon-port-pack` и `cargo-horizon-mod` на том же upstream-коммите:

```bash
cargo build --profile fast --locked -p horizon-port-pack -p cargo-horizon-mod
# Для TLS-прокси облачной среды необходимы системные CA:
cargo build --profile fast --locked -p horizon-port-pack --features ureq/native-certs
```

Без `native-certs` официальный port-tool возвращал `UnknownIssuer` для Modrinth.
Проверка TLS не отключалась. Получен актуальный исходный `.mrpack` из
Actions #42597702544 (89 Modrinth-компонентов, 91 запись файлов). Повторены
команды `import/inventory/fetch/inventory --offline/carry/report`, сборка
общих тегов и официальный SDK build/check всех шести модулей. Все прошли.

**Подтверждено запуском настоящего Horizon 26.3:**

- Сначала базовый сервер достиг `Done (2.262s)` на loopback-порту 25583.
- Затем отдельный сервер с шестью включёнными `.hmod` достиг `Done (2.945s)`
  на `127.0.0.1:25584`. Движок явно сообщил `content from 6 mod(s)`.
- `online_mode=true`, whitelist включён, панель выключена,
  `restart_on_crash=false`. Ни один клиент не подключался.
- В обоих тестах выполнены загрузка чанка, установка золотого блока,
  `save-all flush`, штатная остановка, перезапуск и проверка блока командой
  `execute if block`. Для шести модулей получен `HORIZON_SIX_SAVE_REOPEN_OK`.
- `locate structure betterdungeons:small_dungeon` нашёл структуру;
  `place structure betterdungeons:small_dungeon 0 80 0` в загруженном чанке
  сообщил об успешной генерации. Это ещё не визуальная проверка структуры,
  естественной генерации, лута, спавнеров или всех четырёх YUNG-модулей.
- Оба сервера после проверки штатно остановлены.

**Обнаруженные блокеры:**

- Несмотря на успешную загрузку шести пакетов, `locate biome` не распознаёт
  `terralith:alpine_grove` и `terralith:arid_highlands`. Оба JSON реально есть
  в собранном `.hmod`; движок сообщает только 67 биомов. Полноценная генерация
  Terralith не подтверждена. Нужен разбор регистрации биомов и dimension/noise
  данных в закреплённом движке, а не исключение Terralith из требований.
- Исходный CI-движок пишет `Failed to request Minecraft Services public key`. При этом
  системный HTTPS-клиент успешно читает discovery и publickeys. Ниже описаны
  исправление сборки и повторный серверный прогон; вход лицензированного клиента
  и secure chat всё ещё не проверены. `online_mode` не отключался.

Машиночитаемый итог без ресурсов, миров и сырых логов:
[`SERVER_RUNTIME_RESULT.json`](SERVER_RUNTIME_RESULT.json). Это серверный smoke,
не готовый модпак и не измерение производительности: без игроков TPS/RAM
не характеризуют игровой сценарий.

## Воспроизведение загрузки и подготовки

Новый скрипт разработчика принимает **новый/пустой отдельный кеш**, отказывается
писать в существующую установку launcher, сверяет metadata с upstream lock,
проверяет каждый файл и повторно использует только проверенные загрузки:

```bash
python horizon/tools/fetch_minecraft_inputs.py \
  --cache /path/to/new-input-cache \
  --research-lock /path/to/pinned-horizon/research-lock.json
horizon-prepare --prepare --complete --root /path/to/pinned-horizon \
  --minecraft-dir /path/to/new-input-cache \
  --server-jar /path/to/new-input-cache/versions/26.3/server.jar \
  --java-home /path/to/jdk25 --output /path/to/prepared/26.3
horizon-prepare --check --root /path/to/pinned-horizon --output /path/to/prepared/26.3
```

После описанного выше preflight и SDK-проверок:

1. Выполнить `horizon-server --dir /path/to/new-test init --eula --world test
   --seed 263 --port 25584 --whitelist --yes` (согласие на этот тест уже получено).
2. Через `config set` задать `server.bind=127.0.0.1`, `server.online_mode=true`,
   `server.whitelist=true`, `engine.restart_on_crash=false`, `panel.bind=`,
   абсолютные `engine.path` и `engine.resources`. Не запускать до настройки.
3. Скопировать шесть проверенных `.hmod` в `new-test/horizon-mods/`, записать
   для каждого `mod.<id>:true` в `new-test/horizon-mods.txt` — по умолчанию моды
   выключены. Список ID находится в preflight и JSON-отчёте.
4. `start`, проверить `status --json` и журнал, выполнить команды smoke через
   `cmd`, завершить `stop`. Не использовать старые миры NeoForge.

## Оставшаяся граница PR #8

Даже успешно запущенный сервер с шестью модулями данных не переносит
Java-механики Create/IC2/Incoming и остальных компонентов. Их реализации
и игровые испытания остаются отдельной большой работой. PR #8 остаётся draft,
пока не выполнен выбранный владельцем критерий работающего Horizon-модпака.

## Уточнение Terralith после серверного smoke

Дополнительные испытания проведены в третьей отдельной папке
`/workspace/horizon-runtime/terralith-bridge-test`, порт 25585, с теми же
ограничениями loopback/online-mode/whitelist и выключенным перезапуском при сбое.
Миры предыдущих двух успешных тестов не менялись.

В закреплённом исходнике `Biomes::load` читает только
`data/minecraft/worldgen/biome`; добавленные биомы мира поступают через
`Biomes::with_packs`. Простое наличие `data/terralith/worldgen/biome` в `.hmod`
не доказывает регистрацию биома в мире. Кроме того, в `outside` Terralith
оставлены **35 ванильных биомов, 26 density functions, 18 placed features,
16 noise-файлов и Overworld dimension**. Они существенны для генерации, и
игнорировать их при подсчёте готовности нельзя.

Проверены два варианта локального datapack-моста:

1. 95 новых биомов из carry + явный Overworld stem из outside.
2. 1683 worldgen/dimension/structure-файла из carry и outside, обработанные
   официальным `horizon-port-pack upgrade-datapack` с того же upstream-коммита.
   Он сообщил об обновлении 130 биомов, 481 configured feature, 104 density
   functions, 132 noise, 565 placed features, noise settings, dimension и других
   реестров. Это инструмент обновления **26.2 → 26.3**, а источник TechQuest —
   **1.21.1**; его успешное завершение не доказывает совместимость такого входа.

Оба варианта обнаружены по правильному серверному пути
`<server-dir>/<world-name>/datapacks/` (не клиентскому `saves/<world>`), но
движок завершился с кодом 1: `invalid world generation field: type`.
Перезапуск при сбое отключён; сервер третьего теста не запущен.
Неудачные мосты не включены в основной набор шести `.hmod` и не выдаются
за исправление. Их входы и отчёты оставлены только в локальном стенде.

Следующая необходимая работа — диагностика конкретного несовместимого поля
генератора с минимальным воспроизводящим набором, полноценная миграция
worldgen 1.21.1 → 26.3, затем тест естественных биомов/структур, лута и
повторного открытия мира с этим набором. После этого всё ещё нужны вход
лицензированного клиента, мультиплеер и нативные игровые механики. Закрытие
PR #8 как готового модпака по текущим результатам было бы недостоверным.

## Проверка исправления HTTPS-клиента

Тот же нативный `horizon-server-files::profiles::fetch_profile_key_keys` из
закреплённого upstream успешно получил и разобрал **2 официальных ключа**,
если собрать его с `ureq/native-certs,ureq/proxy-from-env`. Проверка выполнена
реальным сетевым запросом, без аккаунтов/сессий и без отключения TLS.
Без этих feature-флагов серверная сборка не включает доверие системному CA
и автоматическое использование прокси из окружения.

В `horizon-native-runtime.yml` добавлены оба feature-флага и их запись в
build-result. Все четыре инструмента затем **пересобраны локально** из того же
закреплённого upstream за 11 мин 15 с точной командой workflow; tracked-исходники
upstream не менялись. Новая сборка хранится отдельно в
`/workspace/horizon-runtime/native-tools-cloud`, со своими SHA-256 и метаданными.
Ранее скачанные четыре CI-бинарника не заменялись. Новый запуск workflow на
GitHub не выполнялся и не выдаётся за успешный CI.

Все четыре новых инструмента прошли `--help`; новый preparer прошёл `--check`.
Полный новый движок загрузил шесть модулей и достиг `Done`. В течение 20 секунд
наблюдения прежняя ошибка запроса ключей не появилась. В том же изолированном
мире проверены установка алмазного блока, сохранение, остановка, перезапуск и
`HORIZON_CLOUD_SAVE_REOPEN_OK`; сервер штатно остановлен. Вход клиента и secure
chat этим не проверяются.

Для воспроизведения небольшой проверки без компиляции всего движка:

```bash
mkdir -p /path/to/pinned-horizon/crates/horizon-server-files/examples
cp horizon/probes/profile_keys.rs \
  /path/to/pinned-horizon/crates/horizon-server-files/examples/techquest_public_keys.rs
cargo run --manifest-path /path/to/pinned-horizon/Cargo.toml --profile fast --locked \
  -p horizon-server-files --example techquest_public_keys \
  --features ureq/native-certs,ureq/proxy-from-env
```

Проверка ключей не является входом Microsoft и не доказывает возможность
подключения игрока. Следующий игровой прогон требует лицензированного клиента
с выполненным владельцем входом через официальный
Horizon Launcher; токены и пароли в чат или репозиторий не передаются.

## Локализация несовместимости density functions Terralith

Отдельный нативный диагностический пример в локальном upstream
`crates/horizon-world/examples/techquest_density.rs` загрузил ванильные bundles
и поверх них обновлённые функции Terralith: 187 noises и 152 densities.
Настоящий `DensityRegistry::from_json` отверг набор:
`unknown density type: minecraft:weird_scaled_sampler`.
Первый обход отдельных графов ошибочно сообщал об отсутствующих
`minecraft:overworld/continents`, `temperature` и `erosion`: диагностический
пример не учитывал неявный namespace `minecraft`. После исправления обхода
все эти ссылки разрешились без изменения ресурсов. Это уточнение отражено
в JSON-отчёте; переименование функций не выполнялось.

Автоматический upgrader 26.2 → 26.3 не обеспечивает полного переноса старых
графов 1.21.1. Нужны проверенные преобразования старых форматов;
подмена константами, случайное переименование ссылок и отключение Terralith
не считаются исправлением. PR #8 по критерию готового модпака остаётся
незавершённым: 5 partial / 47 not-yet / 39 not-needed / 0 ported.

Следующий подтверждённый этап: [адаптер и реальная генерация Terralith](TERRALITH_RUNTIME_RU.md).
С адаптером сервер достиг `Done`, естественный биом и блок сохранились после
перезапуска. Последующая синхронизация производного `.hmod` восстановила
декодирование 106 tree-features; остаётся разбор 140 отказов placed features.
Деревья и их почва проверены размещением командой и после перезапуска, но
это ещё не завершённый порт. [Отчёт деревьев](TERRALITH_TREE_RUNTIME_RESULT.json).
