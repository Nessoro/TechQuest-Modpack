# Архитектура MVP — Broken Arrow × TechQuest (14.11.2026)

**Статус:** проектирование, не готовый мод. Ветка `experiment/broken-arrow-bridge-mvp`; `main` не затрагивается.

## Основной принцип

Один игрок командует в Broken Arrow, другой действует в Minecraft TechQuest от первого лица. Основная синхронизация — **подразделения и конкретные здания**. Вызов пехоты, бронетехники и позднее авиации; отдача приказов `deploy`, `move`, `defend_building`, `garrison_building`, `evacuate_building`; возвращение результатов.

**Захвата территорий нет.** Не реализуются завоевание деревни как единой зоны, сектора, контрольные круги, процентные шкалы владения районами или начисление очков за район. Нельзя выводить контроль «75% деревни» из числа занятых домов.

## Схема

````text
 [Командир / Broken Arrow]       [Игрок Minecraft]
              |                         |
  [Companion UI — MVP]       [TechQuest Bridge Mod]
              |                         |
              +--- HTTPS/JSON/Auth -----+
                        |
                   [Bridge Server]
             (операции, юниты, здания)
                        |
             [TechQuest Bridge Mod]
                        |
             [Unit & Building Registry]
               /                  \
     [Unit Adapter]           [Building Adapter]
      NPC / техника       гарнизоны и сооружения
           |                        |
      [Minecraft] <----- игра ----> [Minecraft]

 [BA LuaNode / GameAPI] → (?) прямое внешнее подключение,
 только если официально подтверждено/разрешено.
````

## Сущности

### Unit

`unit_id` — стабильный уникальный идентификатор; `side` — сторона; `kind` — `infantry_squad`, `armored_vehicle`, `aircraft` (авиация позже); `minecraft_entity_ids` — привязка к сущностям мира; `order` — текущая задача; `health/status` — подтверждённые сервером показатели.

- Развёртывание только в заданных безопасных точках пополнения, а не мгновенная материализация перед противником.
- Командование NPC и транспортом возможно лишь при наличии проверенного API или разработанного нами адаптера на базе совместимого мода. Пока это открытый технический риск.
- Начать с пехоты, затем бронетехника, затем авиация: полёт и экипажи значительно сложнее.
- Не изменять игровые сущности напрямую из HTTP потока: планировать действия на главном потоке Minecraft сервера.

### Building

`building_id` — уникальный ID конкретного здания, `dimension`, `bounds` (3D-границы коробки/набора комнат), `entrances`, `garrison_slots`, `occupants`, `condition` (`intact` / `damaged` / `destroyed`), `controller`.

- **Занятие:** пехота входит в здание через предусмотренный маршрут/доступную точку. По факту подтверждённого присутствия внутри можно обновить `controller`.
- **Оборона:** юниты держат входы/окна, остаются в здании и используют его как укрытие при поддержке их ИИ.
- **Освобождение:** юниты противника покидают здание или выведены из боя. Если строение пустое, владелец может стать `neutral`; правило консистентно для всех зданий.
- **Спорное здание:** если внутри есть активные бойцы разных сторон, статус `contested`; не считать захваченным автоматически.
- **Разрушение:** `destroyed` блокирует приказ занять внутренние позиции до восстановления/переобозначения. `damaged` может уменьшить количество мест.
- **Важно:** речь идёт о занятости *здания*, а не территории вокруг него. Для вычисления входа/физического присутствия используются геометрические границы самого здания; они не являются зоной территориального захвата.
- Если стандартные деревенские дома не имеют надёжных границ, MVP использует вручную разметку/маркер здания; автоматический анализ произвольных построек — позже.

## Геймплей MVP

1. Игрок Minecraft находится в тестовом поселении, где зарегистрированы 2–4 отдельных здания.
2. Командир через companion UI выбирает доступный тип подразделения и отдаёт приказ `deploy` в допустимой точке.
3. Minecraft сервер создаёт подразделение через проверенный адаптер, регистрирует `unit_id` и отправляет отчёт.
4. Командир задаёт `move` или `garrison_building` с `building_id`.
5. NPC проходят до здания, размещаются внутри и держат оборону, **если интеграция с ИИ это позволяет**. При невозможности возвращается `UNSUPPORTED` — не имитировать успех.
6. При входе/выходе/потере бойцов сервер пересчитывает состояние **конкретного здания**, отправляет `BUILDING_GARRISON_CHANGED` / `BUILDING_CONTESTED` / `BUILDING_CLEARED`.
7. Игрок Minecraft может лично участвовать в обороне/штурме. Результат отображается командиру, но не влияет на территориальный счёт: его нет.

## Bridge Server / безопасность

- Изолированный сервис, два набора прав: `commander` (приказы) и `minecraft` (исполнение, отчёты). При двух компьютерах — закрытая защищённая сеть (например, Tailscale), ограниченный firewall; локальный MVP — `127.0.0.1`.
- Параметры приказов — структурированные данные, не исполняемые строки, в том числе из игрового чата. Схема `../protocol/unit-command.schema.json` задаёт черновой контракт.
- Idempotency по `operation_id`: повторный запрос не должен вызывать второго юнита. Таймаут, срок действия, отключение/повторное подключение, пропавшие сущности, перезапуск мира должны иметь определённые состояния.
- Whitelist допустимых `kind`, максимальное число активных отрядов и машин, ограничения на количество NPC, выбор измерения, координат, времени и существующих/загруженных чанков.
- Отчёты ```ORDER_ACCEPTED```, `UNIT_SPAWNED`, `ORDER_FAILED`, `UNIT_LOST`, `BUILDING_OCCUPIED`, `BUILDING_CLEARED`, `BUILDING_CONTESTED`. `ORDER_ACCEPTED` **не означает**, что юнит дошёл до места.
- Все сетевые запросы обрабатываются асинхронно; создание сущностей, проверка гarrison и игровые события выполняются только в Minecraft server thread.

## Технические зависимости

- Зафиксированы в TechQuest `0.3.3-alpha`: Minecraft `1.21.1`, NeoForge `21.1.264`, Java 21, Superb Warfare `0.8.9.2` и Incoming `3.10.4`. При этом `Incoming` не требуется для захвата зданий и командования наземными отрядами.
- Мод на управляемые NPC-подразделения, экипажи и взаимодействие с Superb Warfare — **кандидат, не подтверждённый API**; сначала совместимость, лицензия, производительность, затем мод-адаптер.
- Генерация поселений: начинаем с готовых/помеченных строений в копии мира. Позже — datapack, регулирующий появление деревень в новых чанках, либо отдельно генерируемые военные здания. Дополнительный генератор не должен менять мир `main` автоматически.

## Broken Arrow

Официальный Scenario Editor с LuaNode/GameAPI — допустимая точка исследования, но **внешний HTTP/IPC из сценария пока не подтверждён**. Без документированного способа передачи событий используем отдельную companion-панель. Никакой инъекции DLL, чтения памяти, обходов EAC или перехвата сетевых пакетов.

## Проверки MVP

- Запрос `deploy` / `garrison_building` / `evacuate_building` с корректными id → проверенные изменения на Minecraft сервере и отчёт в companion UI.
- Повторные и просроченные приказы, потеря сети и рестарт сервера не создают дубликатов.
- Попытка занять несуществующее, разрушенное или переполненное здание отклоняется; два противника в здании → `contested`.
- Игрок Minecraft может вступать в бой и покидать здания; состояние серверное, синхронизация с наблюдателем корректная.
- Ограничить активные отряды, измерять TPS/MSPT и поведение мирогенерации; только в новом тестовом мире/копии.
- Запуск TechQuest без Bridge Mod остаётся без изменений; отдельный CI и отдельный экспериментальный дистрибутив.
- Никаких счётчиков захваченных районов и «зон контроля»: этот функционал исключён.

## За пределами MVP

Полноценный вызов самолётов, авиаудары Incoming, случайная генерация больших городов, полноценный бой пехоты внутри произвольных зданий, автоматическое сопоставление BA/MC координат, встроенный UI Broken Arrow (до подтверждения его официального внешнего API).
